# N1 checklist: the same steps over the real socket

Step N1.7 of the roadmap. A measurement, not a unit test: a running app is asked the same steps as the headless engine, over its loopback control channel, and the two saved files are compared sample for sample. The same OPEN of a 16-bit WAV, `SELECT 1000 2000`, `ACTION edit.delete`, `SELECT 0 500`, `EFFECT invert` and a bare SAVE go through `Remote::from_env` (the app) and through `Headless`; each saved file is read back by a fresh `Headless`, and every sample must be equal. The expected result is 9000 frames in 2 channels. The in-process version of the same check is `apps/wavcraft/src/n1_parity_tests.rs`.

Run it on a Linux machine with a display:

```sh
bash tools/checks/1107-headless-window-parity.sh
```

The script builds the app and the example, starts the app with a fresh home and no file, and runs the example against it. It prints `same=1 frames=9000` and exits 0 when the two files match. Without a display it prints `no display: ...` and exits 2.

The three traps the script and the example handle (the reasons for the checks in them):

1. An open that fails while the open prompt is up can leave `STATE` at `busy=0` before `LASTERROR` is set (`WaveApp::pump_open_queue` in `apps/wavcraft/src/app.rs`). The example reads `STATE` after the OPEN and checks that it names the 10 000-frame, 2-channel `window.wav`.
2. An open the user cancels answers `OK`. The same `STATE` check catches it.
3. `Remote` sets no read timeout on its socket, so a stuck app would hang the example. The script runs the example under `timeout 180` and stops the app with SIGTERM (then SIGKILL after 10 s).
